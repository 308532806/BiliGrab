# BiliGrab v1.7.1

修复 v1.7.0 里一个**会悄悄损坏文件**的问题，建议立刻升级。

## 这个版本修的是什么

v1.7.0 封装出来的 MP4，**音轨可能是空的**。

判断依据不是猜的：拿一条 34 分钟的视频做对照，产物里视频轨 30,829 个样本
完全正常，音频轨的样本数是 **0**。也就是说文件能播、有画面、时长也对，
但**从头到尾没有声音**。纯音频下载更糟：89,223 帧只进去 77,513 帧，
时长从 34:15 缩到 29:43，moov 里连样本表都没有（`MediaExtractor` 读出来
0 条轨），文件根本打不开 —— 而它被标成了「已完成」。

### 根因

B 站与 YouTube 的音频是**分片 MP4**。分片边界上会有几个重复的起播帧，
它们的时间戳贴着前一帧，实测这样的情况：

```
样本 77512  pts=1783529274
样本 77513  pts=1783529297   ← 只隔了 23 微秒，正常是 23220
样本 77514  pts=1783552222   ← 又回到正常间距
```

源文件本身没问题（412 个分片逐个核对，零处回退）。问题在 OPPO 定制的
`OplusMPEG4Writer`：它遇到这种间距不是跳过这一帧，而是**判死整条轨**。

```
E MPEG4Writer: do not support out of order frames
               (timestamp: 1783529297 < last: 1783529319) for Audio track
D MPEG4Writer: Audio track stopped. Status:-1007
```

一条 34 分钟的音频里有 **700 个**这样的帧（412 个分片，每个边界上一两个）。

### 修法

两个改动：

1. **合成视频时丢掉这些重复帧。** 只丢贴在前一帧身上的那一个，
   其余样本时间戳原封不动。丢掉的代价是 23 毫秒静音，位置就在它本来
   该在的地方；不丢的代价是整条音轨消失。

   判据用「间距不到正常间距的一半」。这个规则**只对 AAC 生效**：
   Opus / Vorbis 的帧长本来就变，套用会把好帧当异常扔掉。

2. **仅音频不再重新封装。** B 站和 YouTube 给的音频流本身就是一条完整的、
   能直接播的 m4a。把它拆成样本再用 `MediaMuxer` 写一遍，唯一收益是
   「走同一条代码路径」，代价是凭空多一次可能失败的操作。这条路径现在
   直接复制文件（流式复制，因为工作目录在应用私有区、目标可能在 SAF 那边，
   跨文件系统 rename 会静默失败）。

### 顺带修掉的

- **产物完整性校验以前只在 `stop()` 抛异常时才跑。** 但坏文件恰恰是在
  `stop()` 正常返回的情况下产生的 —— 上面那条无声 MP4 就是这么出去的。
  现在无论 `stop()` 成不成功都验证，而且判据从「有没有 moov」升级成
  「**样本数是不是 0**」：轨在、mdat 有 29 MB、样本表却是空的，
  这种文件以前能过检。
- 修正了完整性校验对**分片 MP4 的误判**。它原本只认 moov 里的样本表，
  而分片文件的样本在 moof 里、moov 里本来就是空的，会把一份正确的文件
  判成坏的。

## 验证

同一条 34 分钟的稿件，同一台手机（OPPO Reno4 5G / Android 12）：

| | v1.7.0 | v1.7.1 |
|---|---|---|
| 仅音频大小 | 29,491,948 字节 | **34,610,750 字节** |
| 仅音频时长 | 29:43 | **34:15** |
| 仅音频样本数 | 77,513 | **89,223** |
| 仅音频能否播放 | 否（0 条轨） | **是** |
| 视频音轨样本数 | **0（无声）** | **88,523** |
| 视频音轨时长 | — | **34:15** |

视频产物用自写的 box 解析器逐个字段核对：`stsz` / `co64` / `stts` / `stsc`
四张表齐全，两条轨的时长都是 34:15，和源文件一致。

## 升级提醒

v1.7.0 下载过的**视频建议重下**（旧文件可能是无声的）——
检查方法很简单：播的时候看有没有声音。
仅音频的旧文件如果大小明显小于预期，也是同一原因。

继续沿用 v1.7.0 的自定义下载目录与下载管理页（实时进度、真实速度、
暂停 / 取消 / 删除记录与残留文件）。
