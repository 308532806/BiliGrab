# BiliGrab v1.8.0

## 修复：删除未完成的下载后，主页那一行卡在百分比

下载时点进「下载管理」，把没下完的任务删掉，再返回主页 —— 那一行的按钮
不会变回「下载」，而是永久停在某个百分比上，只能杀进程重开。

原因是主页只监听了 `DownloadService` 的回调，而删除走的是另一条路：
`TaskStore.remove()` → `notifyProgress()` → `TaskStore.Listener.onTasksChanged()`。
服务端的 `onTaskFinished` 在这种情况下**永远不会触发**，主页自然收不到通知，
它以为自己绑定的任务还在跑。

现在 `MainActivity` 同时实现 `TaskStore.Listener`，在 `onResume`/`onPause`
里注册与注销，并在记录变化时调用 `syncRowsWithStore()`：逐个核对绑定关系，
任务已经不在、或已经不在进行中，就把那一行复位成未选中状态。

判定条件是 `!isActive()` 而不是 `t == null` —— 因为取消一个**排队中**的任务
同样只发记录回调、不发服务回调，只看「记录还在不在」会漏掉这种。

## 新增：多连接并发下载，YouTube 提速约 4.4 倍

YouTube 是**按单条连接**限速的，所以总带宽根本不是瓶颈 —— 这也正是换多少
个 VPN 都没用的原因：问题不在出口，在连接的用法。实测同一条 71 MB 直链：

| 连接数 | 速度 | 相对 |
|---|---|---|
| 1 | 8.14 Mbps | 1× |
| **4** | **35.50 Mbps** | **4.36×** |
| 8 | 27.39 Mbps | 退回 —— 反而更慢 |

因此默认 **4 条**，可在 设置 → 同时下载连接数 里改成 1~8；设为 1 即完全关闭
多连接，退回原来的单连接行为。

真机实测（1080P / 246 MB，走代理）：

```
多连接探测：支持区间，总量 257619653 字节，用时 780ms
多连接下载：总量 257619653 字节，分 62 块（每块 4 MB），并发 4，已完成 0 块 / 0 B
多连接下载完成：245.7 MB / 245.7 MB
```

耗时 34.8 秒，平均约 7.3 MB/s。产物校验：视频轨 38,074 个样本、音频轨 27,331 个
样本，双轨时长一致（10:34）。

### 实现要点

- **4 MB 分块 + 共享工作队列**，而不是把文件切成 N 份静态分给 N 条连接。
  静态切分下快的连接先做完就闲着，整体取决于最慢的那条；共享队列让快连接
  自动多领几块。
- **进度记在 `.journal` 台账里**，每下完一块追加一行，只追加不重写 ——
  断电最多丢一行记录，不会让台账本身损坏。
- **总量一定要探测**，不能拿 yt-dlp 给的 `filesize_approx` 顶上。多连接要按
  总长预分配文件，用估算值定长会导致偏小截尾、偏大补空洞。探测只要一个
  1 字节的 Range 请求。用 `Range: bytes=0-0` 而不是 HEAD —— CDN 常常不在
  HEAD 响应里给 `Content-Length`。
- 服务端不支持区间或探不出总量时抛 `Unsupported`，退回单连接。**退回时必须
  丢弃已预分配的文件**：那个文件长度等于总量、中间却全是洞，单连接会把它当成
  「已下完」。

### 顺带修掉一个我自己引入的缺陷

测续传时发现台账被完全无视：日志显示 `已完成 0 块`，232 MB 从头下一遍。
根因是入队分支在真正开跑之前就把状态改成了 `QUEUED`，等到 `runOne()` 执行时
已经分辨不出「用户点了继续」和「这是新建的任务」。

修法是在入队那一刻把意图单独记下来（进程内集合 + Intent extra 双重兜底），
不再依赖状态推断。

真机验证（下载中途强杀进程，模拟最恶劣的断电场景）：

```
续传判定 status=1 半成品=true 签名一致=true → 续传，video.part 台账=true 大小=232257104
多连接下载：总量 232257104 字节，分 56 块（每块 4 MB），并发 4，已完成 12 块 / 48 MB
多连接下载完成：221.5 MB / 221.5 MB
```

它接上了被杀前的 12 块，而不是从零重下。最终产物 249,464,797 字节，
与独立验证过的单连接产物逐字节一致。

## 变更：右上角入口改成向下箭头

原来用的是列表图标，但它其实通向下载管理。换成下载箭头，含义直白。

## 重新设计应用图标

按自适应图标规范重做。画布 108×108，其中只有中心 **72×72（18..90）** 是任何
图标形状下都保证可见的区域 —— 旧版图标的托盘角落在半径 40.5 处，圆形遮罩下
会被切掉。

新版前景全部顶点收在中心半径 35 以内：粉色渐变底 + 白色下载箭头（箭头杆、
箭头尖、底部横条），带一层偏移 2 像素的柔和阴影；另配纯黑单色版供
Android 13+ 主题图标使用。

## 下载管理页（v1.7.0 起）与本次的配合

管理页能看到实时进度条、真实速度，支持暂停 / 继续 / 取消 / 删除记录和残留文件。
配合本次的多连接改动：

- 进度按**已确认完成的块**上报，所以在极快的链路上看起来是 4 MB 一跳的，
  这是刻意的 —— 报「正在写的字节数」会在暂停后续传时对不上。
- 暂停 / 继续走台账续传，已经验证过。

## 已知限制

- **同一时间只跑一个下载任务**。
- **8 条连接实测比 4 条慢**，别当它能线性叠加。
- 换肤或改主色会触发 `recreate()`。
- 4K / 真彩 / 8K 需要大会员账号权限，目前无法解锁（1080P 匿名可下）。
- 删除**进行中**任务的严格复现尚未覆盖：测试素材下载太快（22 MB/s），
  删除窗口只有几秒。合成阶段的删除已验证通过。

## 安装

`BiliGrab-1.8.0.apk`（versionName 1.8.0 / versionCode 10800），v2 + v3 签名。

覆盖安装需要同签名的旧版本。**OPPO 等机型请用 root 安装**，否则会被系统拦截：

```bash
adb push BiliGrab-1.8.0.apk /data/local/tmp/bg.apk
adb shell "su -c 'pm install -r /data/local/tmp/bg.apk'"
```
