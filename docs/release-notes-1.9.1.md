# BiliGrab 1.9.1

一句话：**视频和音频同时下，不再一个等一个。**

你提的那个问题是对的 —— 旧版本确实是「先下完视频、再下音频、最后合成」，
两段流串着走，音频那几兆完全是在视频后面白等的。

---

## 下载流程改了什么

### 视频与音频改为并行

以前两条轨是一条一条来：

```
[========视频========][==音频==][合流]
```

现在同时开跑，谁先下完谁先等着合流：

```
[========视频========]
[==音频==]            [合流]
```

`DownloadService` 里新增 `downloadTracksConcurrently()`，为两条流各起一条线程
（`biligrab-video` / `biligrab-audio`）。音视频都在时走这条路，
「仅音频」和「没有音轨」的情况仍然走原来的串行分支。

**实测（OPPO Reno4 5G，480P，BV1GJ411x7h7，19.91 MB 视频 + 5.16 MB 音频）：**

| 版本 | 视频流 | 音频流 | 两条轨合计墙钟 |
|---|---|---|---|
| 1.9.0（串行） | 1.27 s | 1.40 s | ≈ 2.67 s |
| 1.9.1（并行） | 2.19 s | 1.39 s | **2.19 s** |

日志里会打一行 `音视频并行：墙钟 Xms，视频 Yms，音频 Zms，省下 Wms`，
省下的就是音频本来要独占的那段时间（实测稳定在 1.2–1.4 s）。

### 两条轨的进度不再互相打架

并行之后进度上报变成两条线程同时进来，直接共享状态会被踩乱。所以：

- `progressLock` 与 `pushLock` 分开。前者管进度记账（快），后者管通知与界面
  推送（慢），慢的不该挡快的 —— 否则音频每写一块都要等视频那边把通知画完。
- `concurrentTracks` 抑制 `Speed.reset()`。不然第二条轨一开始就会把共享的
  速度窗口清零，界面上速度会莫名掉一下。
- 进度推送按 350 ms 节流，但 `force=true`（阶段切换）时不限流。

### 连接数不再开得比活还多

音频那条流只有 5.16 MB、分成 2 块，原来照样开 4 条连接 —— 两条各占一个 4 MB
的块，另外两条领不到活，建连、握手、发请求全是白花的钱。并行时两条轨各开 4 条
就是 8 条同时在跑，其中一半可能根本没活干。

现在起跑前先数一下还有几块没下，连接数取 `min(设置值, 待下块数)`：

```
多连接下载：总量 5408198 字节，分 2 块，并发 2，已完成 0 块 / 0 B
待下 2 块，用不了 4 条连接，改为 2 条          ← 就是这一行
```

### 连接总数封顶

并行时两条轨**各开各的**（这是并行真正省时间的地方 —— B 站 CDN 按连接限速，
音频拿自己那几条比排队等视频空出连接快得多），但两条加起来不超过 8 条。
8 是实测的甜点：单条约 0.5 MB/s，4 条约 4 MB/s，8 条约 2.1 MB/s 中位，
16 条反而掉到 0.99 MB/s。

### 多点免费的完整性校验

`fetchChunk` 现在会顺手看一眼 `Content-Range` 里的总量（这个头本来就在响应里，
不额外花时间），和预期的对不上就退回单连接。防的是 CDN 换了边缘节点、
报出来的总量和预期不一致 —— 那种情况下每块都「刚好」取满、台账照常删掉、
文件正常落盘，只是内容错位或者尾巴少一截。**静默错误**，要播到一半才发现。

## 顺带修掉的一个续传 bug

这个是并行**放大了**的：音频先下完、视频还在跑的时候用户点暂停，
继续时音频那条轨其实已经完整 —— 但它没有台账（下完时删了），
而 B 站 DASH 接口又不给文件大小，所以「这条轨已经下完了」的判断认不出来。

结果就是拿 `Range: bytes=5408198-` 去问一个正好 5408198 字节的文件，
服务端回 416（区间不可满足）。旧代码把 416 当成普通错误抛掉，
备用地址又都带着同一个 Range → 一个一个回 416，
最后报「CDN 返回 HTTP 416，这是哔哩哔哩侧的临时问题，稍后重试」。

**用户点继续，得到的是「网络出问题」，但文件其实已经躺在磁盘上了。**

修法：416 且续传起点正好等于文件长度时，说明这段早就拿完了，当成「已完整」收工。

```
续传判定 status=1 半成品=true 签名一致=true → 续传，video.part 台账=false 大小=20872903
音频轨的区间已取完（起点 5408198 = 文件长度），视为完整
视频轨的区间已取完（起点 20872903 = 文件长度），视为完整
```

实测这次续传总耗时 3.4 s（对比：修复前是 3 个备用地址轮流 416、最终失败）。

## 代价与边界（照例说清楚）

- **总量仍然要探一次**。B 站 playurl 的 DASH 节点不返回 `size` 字段，
  yt-dlp 给的是 `filesize_approx`。多连接要按总长预分配文件，
  用估算值定长长度本身就是错的，所以这次探测（实测 270–570 ms）省不掉。
  我试过让接口给的 size 直接跳过探测，最后把这个改动删掉了 ——
  那是个永远不会生效的死代码。
- **并行只在音视频都下的时候生效**。「仅音频」和「无音轨」还是老路。
- **合流现在是最大头**。实测 2.5–5.6 s，占总耗时 48–74%（视机器发热而定），
  受 `writeSampleData` 限制：视频 5306 个样本、音频 9952 个样本，
  合起来一万五千多次调用。这次没有动它。
- **两条轨的进度是确认块粒度**（4 MB），所以并行时进度条会有跳跃感。
